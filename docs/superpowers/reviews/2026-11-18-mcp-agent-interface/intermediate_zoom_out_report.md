## Ruling on the v1 tool surface

The operator's priority is read + natural-language data entry + full-portfolio import from a statement. Nothing in that asks for a general CRUD API. I rule:

**Stays.**
- All seven read tools, with two conditions: `list_transactions` gets a stated page size and hard ceiling (F), and `get_performance` must not surface `unrealized_pnl` / `realized_pnl`, which are constants (DS-5) — the tool description naming only three fake fields is not enough when success criterion #1 is literally "what is my realized gain in 2025?".
- `stage_import`, `apply_staged`, `discard_staged`, `get_staged`.
- **New:** the pending-batches read-only list in the Access screen (A). It is a strict subset of the deferred UI panel, it reuses the `preview` JSONB that is already being stored, and it is the cheapest thing that breaks the proposer-renders-its-own-review loop.

**Goes, and what the spec must then say.**

1. **`stage_edit` as a separate tool — cut.** Its create half is already expressible as one `stage_import` call with one asset and one transaction, so `stage_import` becomes the single staging entry point. The spec must say so in one sentence in `stage_import` ("single-row entry uses this tool") rather than leaving implementers to discover it. This removes CP-6, SY-21, ST-7's prose rows, the per-element scope matching, and half of the payload surface.
2. **`update_*` — cut entirely.** No requirement asks for it, and an update by a model that picked the wrong id is unrecoverable without a delete, which is also cut. The spec must state the reason and the reinstatement trigger ("an update tool needs the same delete-echo discipline, and needs a reason to exist first"), not just omit it.
3. **`delete_*` — cut entirely.** DS-11 is decisive and the design already owns the argument: the non-goal that keeps `mode=replace` in the web UI because a typed-word confirm is the only honest gate applies with *more* force to a surface where the confirmer is the proposer. Agent-side deletes are weaker than the thing the design excluded. The spec must say: deletes stay in the web UI, an agent that needs one tells the human to do it, and the capability is absent rather than policy-gated — which is the same "cannot be minted" logic the backup non-goal uses, finally applied consistently.
4. **The third scope — cut.** With create-only staging, `write` has no distinct meaning. Scopes become `read` and `import`, plus `apply` from (A). The `kind`→scope prose mapping disappears, and the tool table's Scope column becomes an enumerable column (ST-7, CP-2).

**Kept but gated:** `target.existing` merge stays, because re-importing an updated statement is a real need — but it cannot ship until duplicate matching is defined as `Decimal` equality over named fields (DS-4). As written the rule silently fails on a re-exported `10` versus a stored `10.0`, which is the flagship guarantee failing in the common case.

**Consequence worth naming:** cutting update and delete removes every caller-supplied id from the staging payload except the staged-batch handle. That shrinks the `access.rs` surface, shrinks the new gate script's job, and makes the staging payload structurally identical to the backup bundle nesting — which is what makes the next section cheap.

## Ruling on the two structural alternatives

### (a) rmcp in stateless JSON mode inside Rocket — **investigate, timeboxed, before Workstream 2 is planned. Do not adopt sight-unseen; do not reject.**

The design's rejection rests on one argument — "hand-rolling SSE through a Rocket `Responder` fights the framework" — and stateless mode removes SSE from the problem entirely. Requirements 1–6 need no server-initiated streaming; Non-goals already exclude resources, prompts, sampling and subscriptions. A rejection whose sole stated reason has been removed is a defect in the document regardless of which way the decision lands, and the design's own Verification item about "stateful mode and SSE keep-alive" shows streaming was assumed rather than required.

What it would remove if it works: the second listener, `hyper`/`hyper-util` usage and the version-bump question, the ingress/Service/containerPort/TLS work (DS-14, Stage 5 gap 5), the fifth gate script (ZO-9), the invisible-to-probes problem, Rocket's body limits as a freebie against DS-7, and — if statelessness is real — the `replicas: 1` session coupling.

What it does **not** remove: PATs, staging state, pool/CPU/memory contention (same process either way, DS-6/DS-7 unchanged), and the `tower`/`http` version question (narrower than `hyper`'s, still open). What it **adds**: a hand-written request/response adapter, and a change to the most sensitive inventory in the repo.

Evidence that settles it, as a half-day spike:

1. `rmcp` 3.11 exposes a stateless / no-session server mode that round-trips `initialize` → `tools/list` → one tool call with its own `StreamableHttpClientTransport` **and** with one real third-party client, with no SSE and no `Mcp-Session-Id`.
2. A buffered adapter (method/URI/headers/body in, status/headers/bytes out, no streaming) passes that round-trip in one bounded file. If it needs streaming anywhere, reject.
3. `AuthFairing`'s prefix rule (`auth/fairing.rs:40`, protects by `path.starts_with("/api/")`) is confirmed **inert** for the mount point, so the fairing needs no exemption. If the only way to make it work is to touch the fairing, reject — a bearer token read on the same socket as the cookie surface is exactly what the two-listener design exists to make impossible.
4. `tests/route_coverage_test.rs::no_mounted_route_escapes_the_prefix_rule` (`PUBLIC_NAMESPACES`, `:181`) admits the new namespace by explicit amendment. Note this is a *cost neither Stage 5 nor Stage 7 priced*: the repo has a gate that fails on any new public namespace. But amending one maintained inventory is cheaper and less drift-prone than writing and maintaining a fifth gate script — which is an argument for (a) that the design did not make, and one for (b) that it did not face.
5. The chosen MCP client does not require server-initiated notifications.

If 1, 3, 4 and 5 pass and 2 is bounded, adopt it and delete the second listener's whole cost stack. If any fails, record the failure in the new Alternatives section and the second listener becomes a decided design rather than a default.

### (b) Reuse the backup preview/restore machinery as the single staging path — **partially adopt, as a constraint on Workstream 2; reject the part that cannot work, on the record.**

This is not the alternative Stage 7 framed. `POST /backup/preview` is stateless — it returns a `Plan` and restore re-sends the whole bundle. So the staged-batch row, opaque handle, TTL, single-use flip and user binding still have to be written no matter what. `staging.rs` is not avoidable.

What is adoptable, and should be written as a constraint: the **validate → plan → apply** triple that `backup/mod.rs`, `backup/detail.rs` and `backup/restore.rs` already implement must be the single implementation the agent path calls. No second preview renderer, no second anomaly vocabulary, no second write path. This closes ZO-1, ZO-11 and most of root problem D at once, and it is the answer to the design's own "reuses rather than re-invents" promise, which is currently unfunded.

What must be rejected on the record: **merge into existing rows.** `backup::restore::Mode` is exactly `Copy` and `Replace`, and the source states the reason: merge is "deliberately absent: 'which transaction is a duplicate?' has no clean answer, and a wrong guess silently corrupts a tax ledger" (`restore.rs:22-24`, verified by the orchestrator). Restore also always mints new ids and never matches an existing row (`restore.rs:10-11`, verified). So the agent's `target.existing` + exact-duplicate-skip is precisely the capability the backup module refused — and DS-4 shows the refusal was well-founded, because the duplicate rule as specified is not even well-defined. The spec should say: `target.new` reuses the existing insert path (it is nearly `Mode::Copy` on a sub-bundle); `target.existing` is new code, it is the case backup declined, and it gets reviewed as such.

Evidence that settles the reuse half: a spike showing `backup::detail::detail_from_bundle` renders a plan from a one-portfolio sub-bundle rather than a whole-user snapshot, and that the caps (`MAX_BUNDLE_BYTES`, row ceilings) and the agent caps can be one regime. If `detail_from_bundle` turns out to be hard-coupled to whole-bundle shape, downgrade the ruling to "reuse the flag codes and the plan shape, not the code path" and say which.

## What the design must add that nothing has asked for yet

1. **Name the MCP client.** Four passes have reviewed a design whose central mechanism — the human reads the preview in chat — depends entirely on software the document never identifies. Which client? Does it truncate long tool output? Does it relay a 20k-token preview verbatim or summarize it? Does it retry a timed-out `apply_staged`? The design's own token-economics hole (DS-16) is a symptom; the cause is that the integration partner is unspecified. One paragraph, plus one end-to-end run against that client as an acceptance gate.
2. **Test the premise, not just the plumbing.** The design's founding bet is "the model normalizes the broker statement." Every test in the document assumes the rows are already structured — the e2e test posts a synthetic payload, and the golden fixture asserts the *preview*, not the model's accuracy. Nothing measures whether a real model turns a real statement into correct rows, and there is no baseline or error budget. This is the one assumption the entire design exists to serve and the only one nobody proposes to check. A ten-row manual accuracy run against two or three real anonymized statements, recorded in the spec, is enough to know whether the feature is viable at all.
3. **A threat model that separates three adversaries.** The document reasons about a misreading model and a leaked token, and never names the third: the broker statement is untrusted input to an agent that can write rows. A statement containing text that reads as instructions is the actual prompt-injection path for this feature, and the staged-batch gate is its mitigation — but the design never says so, so the gate will be implemented as a UX nicety rather than as the containment boundary it is. Root problem A becomes much more urgent once stated this way. One paragraph: what we assume, what we do not, and which control answers which.
4. **A decision gate on the plan, not just findings.** Workstream 2 should not be planned until three things are settled: the apply-confirmation mechanism (A), the shared write/preview service (D), and alternative (a). The spec currently lets all three be discovered during implementation, which is how the design ended up with a fifth gate script and a second preview engine. Add one sentence to Sequencing: Workstream 2's plan is not started until those three are recorded in the Alternatives and Costs sections.
5. **Read-side output contracts as deliberate as the write DTOs.** The write path gets `deny_unknown_fields`, a regex and a checksum; the read path gets the word "paginated". For a design whose whole thesis is that the model is the unreliable component, there is no stated bound on what a read tool can pour into a context window, and no stated shape for a page. This is not a performance question — it is the interface contract of seven of the twelve tools.

## Verdict

This is a good design with a bad habit: it earns trust with precise citations and then spends that trust on four load-bearing claims that are wrong, one central mechanism it never specifies, and a safety guarantee it asserts in the passive and enforces nowhere. Nine root problems close essentially all 130 findings, and three of the nine (B, C, G) are document work rather than design work. **Workstream 0 is ready to go to a plan after B and C** — it is genuinely valuable on its own merits, but it must be re-scoped honestly as a breaking live-API change with a frontend prerequisite, not sold as a formalization. **Workstream 1 is ready after A and C** — the token model is sound and the Access screen is well-shaped; only the scope lattice and the apply-confirmation decision are open. **Workstream 2 is not ready**, and should not be planned until three decisions are recorded: what makes apply a control rather than a convention (A), what shared write and preview service the tools call (D), and whether the second listener exists at all (alternative (a)). Cutting `stage_edit`, the update and delete operations and the third scope makes Workstream 2 roughly a third smaller and removes the two places where the design contradicts its own reasoning about destructive writes — the spec gets both smaller and stronger, which is the test this standard exists to apply.
