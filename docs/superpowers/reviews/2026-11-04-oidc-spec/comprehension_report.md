## What this proposes

This spec (1 of 4) adds OpenID Connect authentication to Portfolio Prism by delegating identity to an already-operated Authentik instance: the Rocket backend terminates the authorization-code-with-PKCE flow under `/auth/*`, JIT-provisions a local `users` row keyed on `(issuer, subj)`, and authenticates subsequent `/api` calls with an encrypted Rocket private session cookie carrying `{user_id, token_version}`. On top of that it introduces hard per-user data isolation: `portfolios.owner_id` (rebuilt to `NOT NULL` via the existing column-rebuild helper), a `portfolio_members` table created but not yet written, and a single `src/access.rs` module that is the only permitted way to resolve a portfolio/asset/transaction by caller-supplied id, returning `404` (never `403`) for anything not held. It also authenticates `/api-docs`, adds a per-user in-process token bucket on `/api/assets/lookup`, keeps `GET /` public so Kubernetes probes and the initContainer still pass, and defers sharing (Spec 2), API keys + MCP (Spec 3) and MCP OAuth 2.1 (Spec 4). Local development and CI are meant to keep working through an explicit `AuthMode::Disabled` that is allowed only on an allowlisted Rocket profile.

## How the existing system works, per this document

A Rust/Rocket 0.5 backend (`backend_rust/`) with SQLite via SQLx, plus a React + Vite SPA, served same-origin: in production nginx (frontend container, port 80) proxies `/api` and `/api-docs` to `127.0.0.1:8000`, and in development the Vite proxy does the same, which is why the browser never handles a token. There is currently no authentication of any kind — every `/api` route and the full published OpenAPI document are publicly reachable, and `portfolios` / `assets` / `transactions` have no owner column and use enumerable `INTEGER PRIMARY KEY AUTOINCREMENT` ids. Schema changes happen as startup migrations inside `init_db`, including a crash-safe `migrate_one_column` rename→add→copy→drop rebuild run on a dedicated connection with `legacy_alter_table`; foreign keys are never enabled, so `REFERENCES` is documentation only. `docs/openapi/openapi.json` is committed, regenerated by a documented `cargo run` + `curl` procedure, diffed in CI, and used to generate `frontend/src/types/api.d.ts`; frontend tests use Vitest/MSW. Deployment is a single replica on one PVC, with backend liveness/readiness probes and a `wait-for-backend` initContainer all curling `GET /` on port 8000.

## Findings

1. **Severity**: Blocker
   **Affected Scope**: Requirement 7, Configuration & Deployment (`AUTH_MODE` default), OpenAPI/CI & Frontend Impact, Testing Strategy "Gates"; lines 24, 415–422, 470–476, 522–526
   **Discrepancy Description & Rationale**: The document makes `/api-docs/openapi.json` require authentication (requirement 7) and makes `AUTH_MODE` default to `oidc`, but never says how the OpenAPI spec is regenerated afterwards. The regeneration procedure it points at ("regenerated with the documented `cargo run` + `curl` procedure") is an unauthenticated `curl http://127.0.0.1:8000/api-docs/openapi.json`, and CI's "Generate and Validate OpenAPI Spec" step does exactly that with a bare `cargo run` (`.github/workflows/ci.yml:23-33`); AGENTS.md's version even uses `cargo run --release`, which per this spec additionally hard-errors without `ROCKET_SECRET_KEY`. As written, after this spec lands the CI curl receives the `401` JSON body, the diff fails, and the spec's own stated gate "OpenAPI diff green" is unsatisfiable. The document enumerates env changes for `start.sh` and for `k8s/configmap.yaml` but not for CI or for the documented regeneration procedure. The fix is small (e.g. "regenerate with `AUTH_MODE=disabled ROCKET_PROFILE=dev`", plus a secret key for the release-build variant), but it must be stated, because it is a prerequisite of every future API change. Related unstated behavior: what happens when `AUTH_MODE=oidc` and `OIDC_ISSUER`/`OIDC_CLIENT_ID`/`OIDC_CLIENT_SECRET`/`OIDC_REDIRECT_URI` are absent — presumably refuse to start, consistent with the deny-by-default posture, but the document never says so, and that is exactly the state CI would be in.

2. **Severity**: Major
   **Affected Scope**: Backend Changes §1 (`AuthMode::Disabled` / `bootstrap:dev`) vs §4 Backfill; Requirements 4 and 10; lines 168–176, 279–287
   **Discrepancy Description & Rationale**: Two rules collide in local development. §4 says: if any `portfolios.owner_id IS NULL` and neither `BOOTSTRAP_OWNER_SUBJ` nor `BOOTSTRAP_OWNER_EMAIL` is set, log the orphan count and exit non-zero. §1 says that in `Disabled` mode with no bootstrap variable set, the app instead creates a seeded row with `subj = 'bootstrap:dev'` "so `./start.sh` needs no configuration", and Configuration & Deployment gives `start.sh` only `AUTH_MODE=disabled` and `ROCKET_PROFILE=dev`. A developer with an existing local `portfolio.db` that already contains portfolios therefore hits the refuse-to-start path, which contradicts requirement 10. The document does not state whether the refuse-to-start rule is waived in `Disabled` mode, whether `bootstrap:dev` is implicitly the bootstrap owner for backfill purposes, or in what order `AuthMode` is resolved relative to `init_db` seeding (the `as_user` value depends on a row that §1 says is "created at startup if absent").

3. **Severity**: Major
   **Affected Scope**: Backend Changes §6 closing paragraph; Testing Strategy "migration and probes"; lines 378–381, 515–517
   **Discrepancy Description & Rationale**: The design's stated defence against route drift is "a test that fails when a mounted API route is absent from the table", and the isolation matrix is said to be derived from "the same list" as the §6 markdown table. A test cannot read a markdown table, and the document never states what the machine-readable source of truth is (a `const` route inventory in Rust, a build script that parses the doc, or a hand-maintained test list that can itself drift). Since the document explicitly rules out the OpenAPI diff as the backstop ("the OpenAPI diff in CI cannot catch a route omitted from this table"), this test is the only remaining guard on the chokepoint-discipline claim, so its mechanism is load-bearing and should be specified rather than implied.

4. **Severity**: Major
   **Affected Scope**: Backend Changes §1/§2 (`OidcConfig`), Configuration & Deployment, Rollout step 3, Security Considerations "Probe safety"; lines 143–148, 411–422, 536–538, 455–463
   **Discrepancy Description & Rationale**: The document never says when OIDC provider metadata is obtained or validated — at process start (issuer discovery / JWKS fetch) or lazily on the first `/auth/login`. This matters for two things it does care about: requirement 9 ("tests pass without an OIDC provider reachable") and rollout step 3 ("set `AUTH_MODE=oidc` and the secrets; restart"). If discovery happens eagerly at startup, a mistyped `OIDC_ISSUER` or an unreachable Authentik CrashLoops the pod, and the probe-safety paragraph — which only guarantees `GET /` stays public — would not protect against it. A fresh reader cannot tell whether step 3 is safe to roll back by env alone.

9. **Severity**: Nit
   **Affected Scope**: Backend Changes §1 `FromRequest` claim (lines 178–181) vs Requirement 1
   **Discrepancy Description & Rationale**: Requirement 1 says all `/api/*` routes require an authenticated identity, but the enforcement mechanism described is opt-in per handler ("any handler that takes `user: AuthedUser` is protected"); there is no mount-level fairing or request guard that would reject an unauthenticated request to a route that simply does not take `AuthedUser`. The claim "the type system makes protection impossible to forget" is therefore slightly stronger than the mechanism — it is impossible to forget *on a route that reads the user*, which is not the same as "all `/api/*`". The route-table test (finding 3) is the actual guarantee for requirement 1, and the document would read more honestly saying so.

12. **Severity**: Nit
    **Affected Scope**: Backend Changes §2 CSRF paragraph (lines 221–225)
    **Discrepancy Description & Rationale**: "the existing exact-origin CORS policy remains as a second layer" overstates what CORS contributes against CSRF: CORS governs whether a cross-origin script can *read* a response, not whether a cross-site form `POST` is sent with cookies, so it is not a second CSRF layer in the sense the paragraph uses. The `SameSite=Lax` argument stands on its own; the CORS sentence would be more accurate as a statement about credentialed cross-origin reads.
