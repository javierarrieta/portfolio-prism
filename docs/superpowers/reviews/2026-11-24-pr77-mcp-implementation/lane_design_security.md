## Direct answers to the four questions

**(1) Credential separation.** All four answers are **correct as built**.
- *PAT → session-only `/api` route: no.* `AuthFairing::is_protected` (`auth/fairing.rs:37-39`) matches only `/api/` and resolves via `resolve_caller`, which reads the session cookie and nothing else; `AuthedUser::from_request` never consults `Authorization` (`auth/guard.rs:232` states this as policy). `pat::lookup` has exactly one caller in `src/` — `agent/mount.rs:190`. So a bearer token cannot reach `POST /api/tokens` or `POST /api/staged-batches/<h>/approve`.
- *Session cookie → `/mcp`: no.* `mount.rs:188` `let secret = parts.bearer.ok_or(Status::Unauthorized)?` is the first statement, and the only credential resolution is `pat::lookup` on that string (`mount.rs:190`). The cookie is additionally stripped from the request handed to rmcp (`mount.rs:236-241`). **But the test that claims to pin this cannot fail for that reason — see SEC-1.**
- *Read-scoped token → import: no.* All four import tools call `self.gate(Scope::Import)` as their first statement (`tools.rs:251, 290, 315, 350`); `require_scope` (`access.rs:312`) returns `Err` for a `Credential::Token` lacking the scope. Pinned by `tests/mcp_mount_test.rs:206-227`, which **can** fail (it asserts the parsed tool-result `error` code, and the fixture mints a genuinely read-only token via `pat::mint`).
- *Is `gate()` before any DB work?* **Before, in all eleven tools** — `gate` is the first statement in every tool body (`tools.rs:161, 200, 251, 290, 315, 350, 375, 471, 566, 641, 736`). The only DB work ahead of any gate is the mount's own `pat::lookup` (one indexed `SELECT` on `api_token`, one `SELECT` on `users`, a once-a-minute `UPDATE`) and rmcp's `initialize`/`tools/list`, none of which touch portfolio data.

**(2) Approval gate.** No token-reachable write found. The only writer of `status = 'approved'` is `staging::approve` (`staging.rs:682`), whose sole caller in `src/` is the session route `approve_batch` (`api_routes/staged_batches.rs:187`) — grep over `src/` returns no other writer or caller. Expired cannot apply: read check `expires_at <= Utc::now()` → `Expired` (`staging.rs:1001`) **and** flip predicate `AND status = 'approved' AND expires_at > now()` (`staging.rs:1012`); `approve` itself refuses with `AND expires_at > now()` (`staging.rs:683`). Discarded/unknown status → `_ => return Err(ApplyError::NotApproved)` (`staging.rs:998`). Double apply is closed by `SELECT … FOR UPDATE` (`staging.rs:979-980`) + the conditional flip + the `rows_affected() == 0` re-read (`staging.rs:1020-1043`); a concurrent second applier blocks on the row lock and then reads `applied`. Two residual sharp edges are filed as SEC-5 and SEC-6.

**(3) `/mcp` in-process.** A **panicking tool is survivable** — Rocket 0.5.1 wraps the handler future in `std::panic::catch_unwind` and maps a panic to a 500 (`rocket-0.5.1/src/server.rs:51-58`, "A panic is treated as an internal server error"), so the process and other connections are unaffected; an in-flight `apply` rolls back because the sqlx transaction is dropped uncommitted. An **oversized body is refused correctly** with 413 under the route's own 1 MiB cap (`mount.rs:75, 204-208`), and taking `Data` rather than `Vec<u8>` correctly avoids Rocket's 8 KiB `bytes` default. A **hung client or a slow tool has no bound at all**, and there is **no concurrency limit anywhere in the crate** — SEC-2.

**(4) Pool.** `db.rs:20` `max_connections(5)`, `acquire_timeout` 5 s (`db.rs:44`), `statement_timeout = '30s'` **per statement** (`db.rs:70`). `staging::apply` holds one connection for ~600 sequential round trips. SEC-3.

## Blockers

None on this axis. No path was found by which a token writes portfolio data without a human session, and no credential-crossing bypass exists in the tree.

## Majors

**SEC-1 — `mcp_refuses_a_session_cookie` never sends a cookie and never runs in the only mode that reads one.** `tests/mcp_mount_test.rs:118-130` calls `client("mcp_cookie")` → `common::build_rocket` → `AuthMode::Disabled` (`tests/common/mod.rs:115`), and `rpc(..., None)` sends **no** cookie and no bearer — the request is byte-identical to `mcp_refuses_a_request_with_no_credential` (`:111-115`). `session::read` is consulted only in the `AuthMode::Oidc` arm of `resolve_caller` (`auth/guard.rs:150-160`), so a regression that made `/mcp` honour `pp_session` in production mode would leave this test green. `lib.rs:364` and `tests/route_coverage_test.rs:217-219` both name this test as the sole guard on that failure mode. Fix: add a case built with the existing `build_rocket_oidc` (`tests/common/mod.rs:138`) carrying a signed `pp_session` and no bearer, asserting 401. Escalate to Blocker if the PR body lists the cookie refusal as test-pinned.

**SEC-2 — `/mcp` has no timeout and no concurrency bound, and shares the async runtime with the human's API.** `mount.rs:250` awaits `.handle(http_req)` and `:258` awaits `resp_body.collect()` with no `tokio::time::timeout`; grep over `src/` finds no `Semaphore` and no `spawn_blocking` at all. The CPU-bound tools (`get_tax_summary` → `analytics::build_tax_report`/`undated_summary`, `get_performance` → `StatsEngine`, `get_transaction_pnl` → `TaxLotEngine`) do their decimal math inline on the shared tokio runtime, so one agent looping them starves `/api` on the same process. The only timeouts in the crate are the pricing client's 10 s (`services/currency_service.rs:320,324`), lookup's 10 s (`api_routes/lookup.rs:93,153`) and the DB's per-statement 30 s — none bounds a whole `/mcp` request, and a client that stalls mid-body holds the task. Fix: wrap the handle in a deadline, add a `Semaphore` (2–4 concurrent `/mcp`, 503 + `Retry-After` on exhaustion), move the engines to `spawn_blocking`. Response side is also unbounded — the whole rmcp body is buffered into a `Vec<u8>` at `mount.rs:268`.

**SEC-3 — a token can exhaust the 5-connection pool and turn the human's UI into 503s.** `db.rs:20` caps the pool at 5. `staging::apply` (`staging.rs:963-1090`) holds one connection for the entire transaction: `SELECT … FOR UPDATE`, the flip, revalidation, then per asset a lookup + `existing_keys` `SELECT`, then one `tx_service::insert` per row — up to 50 + 50 + 500 ≈ 600 sequential statements, with `statement_timeout` restarting per statement so nothing bounds the transaction. `stage` additionally holds a connection while blocked in `pg_advisory_xact_lock(user_id)` (`staging.rs:597`). Five concurrent `apply_staged`/`stage_import` calls take the pool; the human's next request then fails inside `AuthFairing::on_request` → `resolve_caller` → `Err` → `/_auth/unavailable` → 503 (`auth/fairing.rs:96-105`), and `guard.rs:222-235` documents that every `/api` request makes **two** such reads. Fix: the SEC-2 semaphore, and/or a separate smaller pool for the agent path, and/or a total deadline around `apply`.

**SEC-4 — no kill switch for a leaked token: `logout-all` deliberately spares tokens and expiry is opt-in.** `auth/routes.rs:314-330` bumps `token_version` and clears the cookie only; `auth/pat.rs` module comment states tokens "deliberately survive it". `api_routes/tokens.rs:37` `expires_in_days: Option<i64>` with `None` = never expires, documented as "the default, and the honest one", and `MAX_EXPIRY_DAYS = 3650` (`:79`). There is no revoke-all and no cap on tokens per user. Net effect: the app's only incident-response action leaves every agent token live, and the default mint mints a credential that never dies. Fix: require a default expiry (e.g. 90 days) when the field is omitted, and add "revoke all tokens" beside `logout-all`.

**SEC-5 — the approval gate approves counts, not rows.** `render_preview` (`staging.rs:443`) emits per asset only `symbol/name/isin/asset_type/currency`, `currency_assumed`, `transactions: <count>` (`:461`) and `first_date`/`last_date` (`:462`). No quantity, price or fee is ever shown, so the human approves "IWDA: 500 transactions" without seeing a single money value. `validate` bounds sign and precision but has no plausibility bound, so `price: "0"` or `quantity: "9999999999999999.999999999999"` passes and lands after approval. The file already established the honest-disclosure pattern for the 25-asset cap ("NOT shown here and will still be written"); the money columns get no equivalent. Fix: add per-asset min/max quantity and price to the preview, or a row-set checksum.

**SEC-6 — `src/agent/tools.rs` is outside the access gate, and its module comment miscounts.** `scripts/check_access_gate.sh:72` sets `HANDLER_DIR="src/api_routes"`; the gate never scans `src/agent`. Yet `tools.rs` resolves caller-supplied ids and issues raw SQL against the three protected tables (`tools.rs:172`, `:654`). Today every such tool calls `access::require*` first, so this is an enforcement gap rather than a live bypass — but nothing stops the next tool from skipping it. The module comment at `tools.rs:12-19` is also wrong twice: five tools re-implement their route's SQL, not three, and `list_portfolios` (`:172`) and `list_transactions` (`:383`) do **not** go through `access::require*` — they use an inline unconditional `p.owner_id = $1` predicate (correct, but not the chokepoint the comment claims). Fix: add `src/agent/tools.rs` to the gate; correct the comment.

## Nits

**SEC-7 — a token can undo a human's approval.** `staging::discard` (`staging.rs:697-707`) sets `status = 'discarded'` for `status IN ('staged','approved')`, and the `discard_staged` tool (`tools.rs:315`) needs only the `Import` scope — documented as "No approval needed to discard". It cannot cause a write, but combined with the 5-pending cap it lets a token force a re-stage/re-approve loop on the human. Consider refusing to discard an `approved` batch from a token.

**SEC-8 — header forwarding is a denylist on the app's only non-session door.** `mount.rs:236-241` drops five names and forwards everything else verbatim to rmcp. Correct today; but any header rmcp later trusts (`forwarded`, `x-forwarded-for`, a future `mcp-*` hint) arrives unfiltered. An allowlist (`content-type`, `accept`, `mcp-*`) would fail closed instead.

**SEC-9 — `tools/list` is ungated.** Any valid token, whatever its scopes, receives all eleven tool names and descriptions via rmcp's router (`tools.rs:770-778` `get_info`; asserted for a read+import token at `mcp_mount_test.rs:150-180`). No data leaks; a read-only token merely learns the import workflow exists. Filter by scope or accept.

## Refutations and accepted risk

- **Magnitude overflow via staged money is not reachable.** `is_canonical_decimal` (`db_types.rs:95-118`) caps total significant digits at `MAX_DECIMAL_PRECISION = 28` and scale at 12, so a 200-digit quantity is refused in `validate` before it is stored. I chased this expecting a TEXT-column overflow; there isn't one.
- **Non-constant-time token check is not exploitable.** `pat::lookup` matches on `secret_hash` equality (`pat.rs:283-289`) rather than a constant-time compare, but the secret is 43 base62 chars from a CSPRNG with rejection sampling (`pat.rs:130-150`) — 256 bits, no dictionary. Accepted.
- **Advisory-lock key-space collision: none today.** `staging.rs:597` is the only `pg_advisory_*` call in `src/`. The key is unpartitioned `user_id`, so a future advisory user would need a class argument. Accepted with a note.
- **`AuthMode::Disabled` opening all of `/api` (including `POST /api/tokens`) is compiled out of release.** `auth/mod.rs:64-70` gates the variant on `debug_assertions`, and `auth/mod.rs:98-103` refuses `AUTH_MODE=disabled` in a release build. Accepted.
- **Handle enumeration.** `new_handle` is 32 CSPRNG bytes hex (`staging.rs:556-562`), and `require_own_staged_batch` answers 404 for both "gone" and "not yours" (`access.rs:239-256`). Not an oracle.
- **Clock skew between app and DB in `apply` is handled.** The flip compares `expires_at` against the DB's `now()` while the pre-check uses `Utc::now()`; the `rows_affected() == 0` branch re-reads the locked row and answers `Expired` rather than `AlreadyApplied` (`staging.rs:1020-1043`). Correct.
