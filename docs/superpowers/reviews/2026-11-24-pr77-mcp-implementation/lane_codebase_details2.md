## Majors

**C2 — Major. `AGENTS.md` bullet 1: "nothing in the engines reads it" is PARTLY false.**
`engines/tax_engine.rs:797` takes `asset_type: &str` as a parameter of `calculate_lots` and writes it into the response at `:873` (`asset_type: asset_type.to_string()` → `AssetTaxSummary.asset_type`). No engine *branches* on it, so the substance survives, but the bullet's justification — "which is the only reason that is tolerable" — is load-bearing and wrong: a junk stored `asset_type` is echoed to the user in every tax-summary response. `stats_engine.rs:353/453/558` only construct it in test fixtures.

**C3 — Major. `agent/staging.rs:1156-1159` asserts a serialisation property the code does not provide; the portfolio cap is bypassable.**
Comment: "It runs on the open transaction, after the batch has been claimed by the flip, so two concurrent applies cannot both count nine and both create a tenth." The flip's `SELECT … FOR UPDATE` (`:981-988`) locks **one batch row**, not the user. `pg_advisory_xact_lock` appears exactly once in the tree (`:597`, inside `stage`), so `apply` takes no user-level lock. Two concurrent applies of two *different* approved batches (up to 5 may be pending) for one user each count 9 under READ COMMITTED and each insert → 11 portfolios, i.e. exactly the unbounded minting the commit claims to close. Separately, `api_routes/portfolios.rs:30` inserts portfolios with no cap at all, so the "backstop" binds only the agent path. Either take `pg_advisory_xact_lock(user_id)` in `apply`'s transaction or correct the comment to say it only serialises re-application of the *same* batch.

**C4 — Major. `backup/detail.rs` still documents the deleted second producer of `duplicate_symbol`, contradicting both the code and the new AGENTS.md bullet.**
`detail.rs:3-4` (module doc): "Two producers, one shape: `detail_from_bundle` … and `owned_detail` … Both return `PlanSide`". `detail.rs:195-197`: "so `owned_detail` pushes in this same order (`no_assets` first, then `duplicate_symbol`)". The PR body and AGENTS.md both claim the half was deleted — the code agrees, two comments in the same file do not. A reader of `:197` will look for a producer that cannot exist.

## Nits

**C5 — Nit. Two money write paths validate to different rules.** `POST /api/backup/restore` types money as `String` (`backup/mod.rs:174-176`), so serde refuses a JSON number — but validation is `Decimal::from_str_exact` (`backup/mod.rs:494-498`), not `is_canonical_decimal`. A bundle can therefore carry a fractional part longer than `MAX_DECIMAL_SCALE = 12` (`db_types.rs:77`), which `strict_decimal_json` refuses on `/api/transactions`, and restore stores the string verbatim. Not a float leak; a divergent money rule the PR body does not mention.

**C6 — Nit. `pg_advisory_xact_lock($1)` is keyed on bare `user_id` with no namespace tag** (`staging.rs:597`). It is the only advisory lock in the tree today, so there is no collision now, but a later feature locking on a different id space (asset, portfolio) would silently share this lock. A two-key `pg_advisory_xact_lock(classid, objid)` costs nothing.
